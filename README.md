# AIOps智能运维实战精品班三期

获课：itazs.fun/21520/AIOps智能运维实战精品班三期

AIOps实战中最普遍的失败，不是模型选错了，而是跳过了一个朴素的前提：系统到底能不能被看清楚。一份行业调研的数字值得放在案头：77%的值班团队每天至少收到10条告警，但超过一半的组织认为其中真正可行动的不足三成。问题不在于AI不够聪明，而在于喂给AI的数据本身是碎的、断的、缺上下文的。实战的第一步，是承认这个前提，然后从告警生命周期的底层开始修补。

检测层：动态基线不是炫技，是止损

静态阈值最致命的后果不是误报本身，而是长期误报对告警信任度的系统性摧毁——值班人员最终会“看到就划走”。实战中的替换方案不需要复杂模型。按指标形态分类适配算法是更务实的路径：波动型用3-sigma配合EWMA平滑，趋势型用多项式回归或孤立森林，季节型用同比振幅或预测类算法。工程上有一条值得遵循的原则：无监督优先。有监督模型需要持续标注和调优，指标形态一旦漂移模型就过时；而箱线图、EWMA、孤立森林这一套无监督体系对形态变化更健壮。建模时取过去约14天数据，检测时对每类曲线跑两种以上算法投票裁决，计算量上升换来的是系统性偏差的消除。

收敛层：字段去重解决不了真正的问题

哈希去重只能合并完全相同的告警，但压垮值班的是字段不同、根因相同的一串告警。一次数据库故障会同时触发健康检查超时、连接池耗尽、依赖它的多个微服务报错、SLO burn rate告警——每条在技术上各自成立，但对人而言描述的是同一件事。实战中需要五类机制配合：四字段哈希去重是底线，关联聚合抑制按业务与对象组合判断，防抖抑制针对CPU、网卡流量等高抖动指标设定周期内出现次数门槛，时间屏蔽覆盖维护窗口，依赖屏蔽基于CMDB拓扑关系阻断衍生告警。这五层的顺序有讲究：先屏蔽窗口内的已知噪声，再聚合关联信号，最后才轮到值班人员看。

处置层：安全红线比自动化率更值得优先设计

一个真实案例提供了可参照的尺度：某订单中心集群将自愈链路跑通后，配置发布错误导致的连接池耗尽故障，从发现到恢复4分12秒，人工只做了两次操作——确认根因、点击回滚。更激进的案例中，OOM与连接池耗尽的MTTR从20至35分钟压缩到3至4分钟。但这两个案例的共同前提是分级审批被严格执行：低风险的单Pod重启全自动，中风险的扩容走审批，高风险的配置变更与回滚必须人工确认，数据操作类故障仅告警不自动处置。

中国广电四川公司的实践同样指向这一分寸：平台上线后运维团队从近百人精简至21人，故障处理效率提升50%以上，但核心设计是“多智能体协同+人工确认”的半自动模式，而非无人值守。AIOps实战的成熟度，不取决于自动执行了多少动作，而取决于每一次自动执行是否都有回滚方案和审计痕迹。

AIOps的竞争力不在模型参数，而在数据管道的厚度与安全边界的清晰度。先让告警说人话，再让收敛做减法，最后才谈处置的分寸。顺序反了，智能运维不过是把人工救火的现场换成了AI救火的现场。
